1Philosophy & Design

1.1 What is Stratum?

Stratum is a cloud persistence framework built for long-haul operations that require resilient, covert communication channels. It is not a general-purpose C2 framework, a post-exploitation toolkit, or an initial access platform. Its role is precise: establish a persistent encrypted channel on a target environment and maintain it reliably over extended time horizons — weeks, months, or longer — while remaining operationally silent between uses.

The framework's primary value is as a fallback and persistence layer. In a mature engagement, primary C2 infrastructure gets burned — by incident response, domain takedowns, certificate revocation, or IP blocking. Stratum is designed to survive all of these events because it has no infrastructure of its own to burn. When the primary is gone, Stratum is still there.

Design Philosophy
Stratum does one thing extremely well: maintain a persistent, encrypted, covert communication channel over cloud storage. It is not a Swiss Army knife. The agent has a focused set of built-in capabilities (persistence, sysinfo, file transfer, shell pass-through) and is intentionally not designed to grow beyond that scope.

1.2 The Dead-Drop Paradigm

Traditional C2 frameworks run a server — a process listening on a port, requiring a domain, a TLS certificate, and IP infrastructure that can be taken down. Stratum eliminates all of this by using cloud storage as the communication medium.

Traditional C2: Target ──HTTPS──► Attacker's server ◄── Operator (domain, IP, cert, port) One takedown kills the channel. Stratum (dead-drop): Target ──HTTPS──► Dropbox / OneDrive / S3 / etc. ◄──HTTPS── Operator (legitimate cloud storage API) Nothing to take down. No exposed infrastructure. Traffic is indistinguishable from cloud sync.

The "dead drop" is a private folder in a cloud provider account containing three files: input.txt (operator writes encrypted commands), output.txt (agent writes encrypted responses), and heartbeat.txt (agent writes periodic status). The agent polls on a configurable interval. From a network perspective, this is an HTTPS POST to api.dropboxapi.com — identical to a user syncing a document.

1.4 Key Differentiators

Most C2 frameworks share a common assumption: the attacker controls a server. Block the server — kill the implant. Stratum is built around the opposite premise: route through infrastructure the defender cannot block. Everything else follows from there.

Five capabilities distinguish Stratum from every other open-source framework in this space:

① The channel is structurally unblockable

A SOC that wants to silence Sliver blocks the teamserver domain or IP. A SOC that wants to silence Stratum has to block Dropbox, OneDrive, Google Drive, SharePoint, and S3 — which means blocking productivity tools used by every employee in the organisation. That is not a firewall rule; it is a business decision no enterprise will make. The dead-drop architecture does not try to evade detection. It operates on infrastructure the defender has already decided to trust, permanently.

② Five cloud providers, one keypair, one wizard

Dropbox, OneDrive (Microsoft Graph), Google Drive, SharePoint, and S3-compatible object storage all share the same cryptographic wire format and the same RSA keypair. Switching providers mid-engagement takes minutes and does not require touching the agent. No other open-source framework ships five enterprise-whitelisted cloud backends out of the box, unified under a single protocol.

③ Six agent formats from a single deploy flow

From one wizard run: .sh (bash, zero dependencies), .ps1 (PowerShell 7+ / .NET 6+), PE and DLL launchers, musl-static ELF, flat x64 shellcode, and a fully in-process Rust native agent — all sharing the same session and cloud channel. The operator never touches a compiler, sets an environment variable, or manages a keypair manually. This is the sharpest practical differentiator: it puts compiled cross-platform agents within reach of operators who are not developers.

④ /persist probe — know before you install

Before writing a single registry key or cron entry, the operator runs /persist probe. The agent checks every persistence technique at the current privilege level — scheduled tasks, registry run keys (HKCU/HKLM), startup folder, systemd user/system, cron, rc.local — and returns a per-technique feasibility report. Nothing is written. No artifacts are left. The operator sees exactly what is available on that specific host, then installs only what will succeed. No other framework provides a non-destructive persistence feasibility audit as a first-class command.

⑤ Guardrails baked into every agent at deploy time

Operational safety features are not bolt-ons — they are configured in the wizard and compiled permanently into every artifact:

  • Kill date: agent self-destructs (removes persist, deletes binary) on a configured date. No manual cleanup required after engagement end.
  • Maintenance window: beacon only during configured hours — silent during business hours, active at night.
  • Log-normal jitter: beacon intervals drawn from a log-normal distribution rather than a flat random range — the natural distribution of legitimate application polling, resistant to timing-based detection.
  • Compile-time stub secret + ephemeral stage-2: the key that unlocks the stage-2 payload is baked into the stub at compile time and never uploaded to cloud. The stage-2 itself is deleted from cloud on first agent heartbeat. Obtaining cloud credentials after deployment recovers nothing.
  • Shannon entropy correction: script artifacts are measured and padded with natural-language text until H ≤ 5.0 b/B — below the threshold used by common AV scanners to flag packed payloads.
  • MIME boundary randomisation: per-deployment unique multipart boundary in the Rust agent binary eliminates a static string fingerprint.
Positioning
Stratum is not a replacement for Cobalt Strike, Sliver, or Havoc. It is the persistence layer underneath them — the channel that survives when the primary C2 gets flagged, the domain gets blacklisted, or the beacon process gets killed. Deploy Stratum alongside your primary framework on day one. Use it on day four when everything else is gone.

2Cryptographic Protocol

2.1 Hybrid Encryption Design

Every byte of C2 traffic between operator and agent is end-to-end encrypted using a three-layer hybrid scheme. The outer layer provides forward secrecy via Epoch ECDH (X25519) key agreement with a KDF chain ratchet; the middle layer provides command authenticity via RSA-4096 PSS signatures; the inner layer provides bulk encryption via AES-256-GCM with per-message fresh keys. An RSA-4096 key pair is generated per deployment and is never reused across sessions. The private key never leaves the operator machine; the public key is split into four fragments and baked into the agent at compile time.

Three encryption layers
Layer 1 — Epoch ECDH (forward secrecy): X25519 key exchange per check-in cycle. Each epoch derives a fresh epoch_key via HKDF-SHA256. A KDF chain (HMAC-SHA256) ratchets forward per message for anti-replay and fork detection.
Layer 2 — RSA-4096 (authentication): RSA-PSS-SHA256 signs server→agent commands. The agent verifies the signature before decrypting, guaranteeing command authenticity.
Layer 3 — AES-256-GCM (bulk encryption): Per-message fresh AES key, wrapped with the current epoch_key instead of a static session key.
The stage-2 payload / config blob (stub-secret channel) also uses AES-256-GCM. The local hw-keyed blob on disk (DPAPI on Windows, OpenSSL CBC on Linux) is a separate independent layer and is unchanged.

This design provides four security properties simultaneously:

  • Command authenticity — commands can only be issued by the holder of the RSA private key. A compromised cloud account cannot inject fake commands.
  • Response confidentiality — responses are encrypted with the current epoch key and can only be decrypted by the server. A compromised cloud account cannot read agent output.
  • Forward secrecy — each check-in cycle performs a fresh X25519 key exchange, deriving a new epoch key via HKDF. Previous epoch keys are destroyed. Compromise of the current key does not expose past traffic.
  • Anti-replay & fork detection — the KDF chain ratchet produces a monotonic counter and per-message authentication tag. Replayed or out-of-order messages are detected and rejected.

2.3 Command Wire Format (v2)

Commands are written to input.txt in the cloud folder as raw binary (v2 wire format). The agent reads the file, deletes it atomically, then decrypts. If decryption or signature verification fails, the agent writes a KM:<timestamp> marker to the heartbeat file and discards the input.

input.txt — v2 binary wire format (server → agent)
# Binary envelope with version byte 0x02:
#
#   [0x02]                    — version byte (1 byte)
#   [epoch:4 LE]              — epoch counter (uint32)
#   [server_eph_pub:32]       — server's X25519 ephemeral public key
#   [wrapped_len:4 LE]        — length of wrapped AES key blob
#   [wrapped_aes:N]           — GCM(epoch_key, random_aes_key) — nonce(12)+ct+tag(16)
#   [payload_len:4 LE]        — length of GCM payload
#   [GCM_payload:M]           — GCM(random_aes_key, JSON task) — nonce(12)+ct+tag(16)
#   [RSA-PSS signature:512]   — RSA-PSS-SHA256 over (wrapped_aes || GCM_payload)
#
# epoch_key  — derived from X25519 DH between server and agent, rotated per cycle
# server_eph_pub — agent uses this to rotate to the next epoch on its next check-in
# PSS sig    — signed with server private key; agent verifies before decrypting
#
# Agent: parse header → epoch rotate if needed → RSA-PSS verify sig →
#        GCM-unwrap aes_key with epoch_key → AES-256-GCM decrypt payload
Agent → Server wire format (heartbeat.txt / output.txt)
# Binary envelope with version byte 0x02:
#
#   [0x02]                    — version byte (1 byte)
#   [epoch:4 LE]              — current epoch counter (uint32)
#   [agent_eph_pub:32]        — agent's X25519 ephemeral public key
#   [counter:8 LE]            — KDF chain counter (uint64, monotonic)
#   [chain_tag:32]            — HMAC-SHA256 authentication tag from KDF chain
#   [GCM_payload:N]           — GCM(epoch_key, plaintext) — nonce(12)+ct+tag(16)
#
# Server: verify chain_tag (anti-replay) → decrypt with epoch_key
# If epoch > server's epoch: server rotates via DH(server_eph_priv, agent_eph_pub)
Decrypted AES-GCM plaintext — JSON task envelope
# After epoch_key GCM-unwrap + AES-256-GCM decrypt, the plaintext is a compact JSON object:
{"id":"<cmd_id>", "type":"<task_type>", "args":{...}}

#   shell          — execute shell command (all agents)
#   sysinfo        — refresh and upload system info (all agents)
#   env            — dump process environment variables (all agents)
#   sleep          — update beacon interval (all agents)
#   jitter         — update jitter percentage 0–50 (all agents)
#   upload         — push file from server to target (all agents)
#   download       — pull file from target to server (all agents)
#   exfil          — bulk file pull by glob pattern (all agents)
#   timestomp      — copy timestamps from a reference file (all agents)
#   timestomp_set  — set timestamps to explicit ISO-8601 value (all agents)
#   persist_probe  — probe all/selected persistence techniques (script agents)
#   persist_install— install persistence technique (script agents)
#   persist_remove — remove persistence technique (script agents)
#   persist_status — check status of technique (script agents)
#   persist_action — shorthand dispatch via schtask-logon (script agents only)
#   blobsave       — force re-cache of hw-keyed ddb blob (script agents only)
#   exit           — graceful agent shutdown, no artifact cleanup
#   kill           — remove all persistence + wipe blob + exit
#
# "exit" is the wire type for /stop; "kill" is the wire type for /kill.
# persist_action and blobsave are never dispatched to the Rust agent.

Session Key, Pre-Key Pool, and agent_id

Every Stratum agent embeds a per-deployment 256-bit session key at build time. In the v2 protocol, the session key serves as the HKDF salt for bootstrapping the first epoch key (Epoch 0). It is NOT used to directly wrap AES keys — that role belongs to the rotating epoch_key derived from X25519 DH.

The pre-key pool (8 × X25519 keypairs) enables the first epoch bootstrap without a direct server-agent handshake. The agent picks a pre-key public key and performs DH with its ephemeral private key. The server iterates its pre-key private keys to find the matching one.

The agent_id is SHA256("stratum-agent-id:" || session_key) — deterministic on both sides, used as the HKDF info parameter for chain key derivation. This binds the KDF chain to the specific session.

In staged-enc mode the stub hands the session key to the stage-2 payload via the _SS_K environment variable, which is unset immediately after reading. In stageless-enc and stageless-plain modes, the session key is baked directly into the binary.

2.5 Key Derivation & Entropy Engineering

PBKDF2 Iterations

All symmetric key derivation in Stratum (stage2/config enc, local hw-keyed blob) uses PBKDF2-HMAC-SHA256 with 210 000 iterations. This applies uniformly across:

  • Python wizard (providers/_wizard.py, providers/_crypto.py)
  • Rust native agent (crypto_compat.rs, const ITER: u32 = 210_000)
  • Bash stubs (-iter 210000 flag to openssl for CBC blob; 210000 in Python GCM inline)
  • PowerShell stubs (Rfc2898DeriveBytes(pass, salt, 210000, SHA256))

210 000 iterations meets OWASP 2023 minimum (120 000) with comfortable headroom. The iteration count is the same for both the GCM stage2 channel and the CBC local-blob channel — consistency prevents accidentally using a weaker setting in one path.

Entropy Engineering

High-entropy data embedded in PE/ELF binaries is a primary detection signal for tools like Detect It Easy (DIE) and Manalyze. A section with Shannon entropy above 6.5 b/B is a strong indicator of packed or encrypted content. Stratum addresses this at the artifact generation step — not as an afterthought.

How it works: after generating scripts, the wizard measures the Shannon entropy (H) of the entire file in bits-per-byte. If H exceeds the 5.0 b/B target, the wizard appends a block of natural-language padding text (~128 KB, H ≈ 4.4 b/B) and re-measures. This continues until H ≤ 5.0 b/B. The padding text is carefully chosen to be syntactically plausible system utility documentation, blending with legitimate software strings.

The Rust native agent includes a 128 KB entropy pad compiled directly into .rodata via a #[link_section] attribute. This dilutes the entropy of the adjacent high-entropy script bytes from the embedded agent payload.

2.6 Forward Secrecy (Epoch ECDH + KDF Chain)

Stratum v2 implements true forward secrecy using an Epoch ECDH ratchet (outer ratchet) combined with a KDF chain (inner ratchet). This design ensures that compromise of the current session state does not expose any past traffic, and that message replays and agent forks are detected.

Outer Ratchet — Epoch ECDH (X25519)

Each check-in cycle performs a fresh X25519 Diffie-Hellman key exchange. The resulting shared secret, combined with the previous epoch key as HKDF salt, derives the new epoch_key. Previous epoch keys are destroyed.

─── Epoch Ratchet ───────────────────────────────────────────────────────── Epoch 0 (Bootstrap) │ Agent generates ephemeral X25519 keypair (eph_priv, eph_pub) │ Agent picks prekey_pub[0] from baked pre-key pool │ shared = X25519(eph_priv, prekey_pub[0]) │ epoch_key₀ = HKDF-SHA256(shared, salt=session_key, info="stratum-epoch-0") │ chain_key₀ = HKDF-SHA256(epoch_key₀, salt=agent_id, info="stratum-chain-v1") │ │ Server: iterates prekey_privs[0..7], tries X25519(priv[i], agent_eph_pub) │ until HKDF output matches → bootstraps same epoch_key₀ + chain_key₀ │ Epoch N → N+1 (Rotation) │ Server sends server_eph_pub in command v2 header │ Agent: generates new eph keypair │ shared = X25519(eph_priv_new, server_eph_pub) │ epoch_key_{N+1} = HKDF(shared, salt=epoch_key_N, info="stratum-epoch-{N+1}") │ chain_key_{N+1} = HKDF(epoch_key_{N+1}, salt=agent_id, info="stratum-chain-v1") │ │ epoch_key_N destroyed (prev_epoch_key kept for one cycle only, │ in case of in-flight messages encrypted with old key) │ Key derivation chain: X25519 shared secret │ ▼ HKDF-SHA256(ikm=shared, salt=prev_epoch_key, info="stratum-epoch-N") │ ├── epoch_key (wraps per-message AES keys) │ └── HKDF-SHA256(ikm=epoch_key, salt=agent_id, info="stratum-chain-v1") │ └── chain_key (feeds inner ratchet)

Inner Ratchet — KDF Chain (HMAC-SHA256)

Within each epoch, the chain key ratchets forward on every message. This provides per-message authentication, a monotonic counter for anti-replay, and fork detection (two agents with the same initial state will diverge after the first message).

─── KDF Chain Advance ───────────────────────────────────────────────────── Per message (agent → server): │ msg_key = HMAC-SHA256(chain_key, 0x01) │ chain_key' = HMAC-SHA256(chain_key, 0x02) ← ratchet forward │ tag_input = counter (uint64 LE) || gcm_payload │ chain_tag = HMAC-SHA256(msg_key, tag_input) ← per-message auth │ counter += 1 │ Verification (server side): │ Server advances its chain_key to match claimed counter │ Recomputes chain_tag — must match │ Allows skip of up to 10 messages (MAX_SKIP) for lost heartbeats │ Rejects: counter < server_counter (replay) │ counter > server_counter + MAX_SKIP (desync / fork) │ tag mismatch (tampering / wrong key) Properties: ✓ Forward secrecy — old chain keys cannot be recovered from current state ✓ Anti-replay — monotonic counter rejects duplicate messages ✓ Fork detection — divergent chain states produce mismatched tags ✓ Ordering — out-of-order messages beyond MAX_SKIP are rejected

3.3 Native Rust Agent (agents/native/rust/)

The native Rust agent compiles to fully self-contained binaries with no interpreter dependency. All C2 logic, cryptography, and provider transport are compiled into the binary. Source modules:

3.4 Shellcode & Loaders

Shellcode (agents/native/shellcode/): Compiles to x86_64-unknown-none with OUTPUT_FORMAT(binary) via a custom linker script, producing a flat position-independent blob with no PE/ELF headers. The blob is a reflective PE loader — it embeds the compiled native Rust agent EXE (agent.exe, MSVC-ABI) and loads it directly into memory at runtime without writing anything to disk or spawning any interpreter process.

Execution sequence inside the blob:

 1. _start()  →  CreateThread(agent_thread)  →  returns immediately

   agent_thread:
 2. PEB walk  →  locate KERNEL32.DLL base (ROR13 hash of module name)
 3. Export scan  →  resolve VirtualAlloc / VirtualProtect / LoadLibraryA / GetProcAddress
 4. VirtualAlloc(RW, SizeOfImage)  →  allocate image-sized region
 5. Copy PE headers + sections to their virtual addresses
 6. Apply base relocations  →  IMAGE_REL_BASED_DIR64 entries patched with delta
 7. Resolve IAT  →  LoadLibraryA per DLL + GetProcAddress per import
 8. VirtualProtect per section  →  .text→RX  .data→RW  etc.
 9. wipe_embedded_pe()  →  VirtualProtect(.rodata, RW) + volatile memset(0)
10. TLS callbacks (if any)
11. Call OEP as DLL_PROCESS_ATTACH  →  agent C2 loop starts
Step 9 — Post-load .rodata wipe
After the PE is mapped and running in its own VirtualAlloc region, the original embedded bytes in the loader's .rodata are no longer needed. The loader makes the page temporarily writable via VirtualProtect, zeroes all bytes with ptr::write_volatile (preventing LLVM dead-store elimination), then restores the original protection. This eliminates the MZ/PE signature and all agent strings from the loader's memory region — defeating post-execution memory scanners (pe-sieve, Moneta) that would otherwise find a full PE image in .rodata. The loaded agent is unaffected — it runs from its own independent region.
Requires MSVC toolchain
The .bin shellcode embeds agent.exe and is therefore built after the EXE compilation step. If the MSVC toolchain (clang-cl + lld-link + xwin SDK) is not available, the .bin artifact is skipped — the wizard prints a clear warning. All other artifacts are unaffected.

Loader compatibility: The blob is standard x64 PIC shellcode — compatible with any external loader that accepts raw shellcode: Cobalt Strike aggressor scripts, Havoc/Sliver stagers, Donut, sRDI, or any custom loader written in C/Rust/Nim/Go. The contract is simple: the blob is position-independent, starts at offset 0, and assumes only that it runs inside a Windows x64 process.

ELF Loader (agents/native/linux/): A musl-static ELF that embeds the bash agent script at compile time via include_bytes!(env!("STRATUM_AGENT_PATH")). Execution chain on the target:

1. memfd_create(".", 0)  // anonymous kernel memory fd (SYS_319)
2. write script bytes to fd
3. exec bash from "/proc/self/fd/<n>"  // script bytes never touch disk

// Fallback chain if memfd unavailable:
4. write to "/dev/shm/.<pid>", exec, delete
5. write to "/tmp/.<pid>", exec, delete

The child bash process sees the script from /proc/self/fd/n, which appears in ls /proc/PID/fd/ but has no corresponding path in the filesystem. The script content is never written to any filesystem path.

PE Loader (agents/native/windows/): A PE/DLL that embeds the PowerShell agent and executes it via CreateThread → PowerShell in-process. Can be invoked via rundll32.exe agent.dll,Run or regsvr32 /s agent.dll.

Why The Gaps Exist

Bash has no /creds module. Credential harvesting requires binary protocol manipulation (SMB2/NTLMSSP handshake, ASN.1/DER encoding, SPNEGO wrapping), in-memory cryptographic operations (AES-GCM, DPAPI, RC4/DES for SAM), and concurrent I/O (TCP listeners + UDP poisoners running alongside the beacon loop). Bash has no native support for any of these — implementing SMB2+NTLMSSP in pure bash would require thousands of lines of printf/xxd hex manipulation with no type safety, and would produce a fragile, unmaintainable module with no realistic path to correctness. The Rust native agent runs on Linux with full /creds support including in-memory SAM-equivalent (/etc/shadow parsing), SSH key harvesting, browser credential extraction, and the complete listener/poisoner stack. For Linux targets that need credential harvesting, deploy the Rust agent.

Bash has no /bof, /assembly, /assembly-amsibypass, /memexec, /script, /script-amsibypass. In-memory execution (COFF loading, CLR hosting, reflective PE/ELF loading) and fileless script execution require capabilities that are fundamentally impossible in a shell interpreter. These capabilities exist only in the compiled Rust agent.

PowerShell /creds has implementation-level differences from Rust.

  • SAM extraction: Rust reads SAM/SYSTEM hives in-memory via registry API with REG_OPTION_BACKUP_RESTORE — zero processes spawned, zero files on disk, zero command-line telemetry. RtlAdjustPrivilege auto-enables SeBackupPrivilege, so SAM works from elevated Admin (not just SYSTEM). PS1 uses reg.exe save to dump hives to temp files, stages them for offline cracking with secretsdump.py, then deletes the temp files. The PS1 approach leaves brief forensic artifacts (temp hive files, reg.exe in process logs) that the Rust approach avoids entirely.
  • Coercion: Rust implements both SpoolSample (MS-RPRN) and EfsRpc (MS-EFSR) on Windows, plus SSH-agent hijack and Kerberos ccache enumeration on Linux. PS1 implements SpoolSample only (Windows-only agent).
  • Listeners: Rust runs SMB/HTTP listeners as dedicated threads — connections are accepted and processed in real-time regardless of beacon sleep interval. PS1 uses a poll-based architecture where pending connections are checked once per beacon cycle. With a 60-second sleep, a client connection arriving at second 1 will not be processed until second 60. For low-sleep deployments (5–15s) this is operationally acceptable; for long-sleep deployments (60s+) the Rust agent is strongly preferred for listener tasks.
  • Harvest cross-platform: Rust harvest covers both Linux (SSH keys, GPG, cloud creds, NetworkManager WiFi, /etc/shadow, Kerberos ccache, GNOME Keyring, browser profiles) and Windows (DPAPI, Chrome/Edge, Firefox, WiFi, RDP, Vault, cloud creds, FileZilla, mRemoteNG, PowerShell history, Git). PS1 covers Windows only.

PowerShell has no /bof, /assembly, /assembly-amsibypass, /memexec, /script, /script-amsibypass. While PowerShell can theoretically host CLR assemblies and P/Invoke native code, reliable COFF loading, reflective PE execution, and fileless script piping require low-level control over memory layout that PowerShell's managed runtime does not provide safely. The Rust agent implements these as compiled native code with direct control over memory allocation and protection flags.

Operational recommendation
Deploy the Rust native agent for all new sessions. It is the only agent supporting the v2 protocol (forward secrecy), and the only beacon with complete feature coverage on both platforms. Script agents (bash, PowerShell) use the v1 protocol and cannot connect to a v2 server.

4Deployment Modes

Stratum supports three delivery architectures. The choice determines how the agent payload reaches execution on the target, and what survives a disk forensic acquisition.

4.1 Staged-Enc

Staged-Enc

A small stub is delivered to the target. The stub has a 256-bit stub_secret baked into it at compile time. On first execution, the stub checks a local hw-keyed cache (ddb blob); on miss it downloads stage2.enc from the cloud, decrypts it with the baked-in secret, and executes the full agent entirely in memory. The secret never leaves the binary — no key fetch from cloud.

4.5 Decision Guide

  • Default choice for any production deployment: stageless-enc. Maximum OPSEC: config and stub_secret are both in the binary, nothing sensitive ever touches cloud storage. Works offline on every run after the binary lands on target.
  • Need to update payload without re-delivery: staged-enc. Replace stage2.enc in the cloud folder at any time; on the next ddb-miss execution the stub picks up the new payload. stub_secret stays baked in the already-delivered stub — no re-delivery of the stub needed for payload updates.
  • Targeting an air-gapped or fully offline environment: stageless-plain. No cloud access ever. Accept that credentials are readable from the binary.
  • Testing / lab use: any mode. stageless-plain is simplest to debug.

5Persistence Engine

5.1 Protocol Design

Stratum's persistence engine is built around a multi-technique protocol that separates capability probing from installation. Before any persistence technique is installed, the agent performs a non-destructive feasibility check. Only techniques confirmed available at the current privilege level are offered for installation. This prevents failed install attempts from leaving forensic traces — partial registry keys, half-created scheduled tasks, or incomplete service configurations that IR teams find during investigations.

Each technique is independently addressable by a string ID (e.g. schtask-logon, systemd-user) and supports four operations: PROBE, INSTALL, STATUS, REMOVE. All techniques are individually testable, installable, and removable, giving the operator surgical control over the persistence posture.

6.2 Transport Interface Contract

Every cloud provider in Stratum implements a three-method abstract interface. This is the entire surface area a new provider must implement:

class BaseTransport(ABC):
    def upload(self, path: str, data: bytes) -> bool: ...
    # Write `data` to cloud path `path`. Return True on success.

    def download(self, path: str) -> Optional[bytes]: ...
    # Return bytes at cloud path, or None if not found / error.

    def delete(self, path: str) -> bool: ...
    # Delete cloud path. Return True on success.

The transport layer in agent scripts follows the same contract: _upload(), _download(), and internally _token_refresh() for OAuth2-based providers. Token expiry handling (retry on 401/expired token) is the responsibility of the transport layer, not the C2 core.

The heartbeat uses the same v2 epoch-encrypted wire format as command responses (see §2.3). The heartbeat plaintext is a pipe-delimited string, encrypted with the current epoch_key and authenticated by the KDF chain (chain_tag + counter). The server decrypts the heartbeat using the shared epoch state and verifies the chain tag for anti-replay. On the first heartbeat (Epoch 0 bootstrap), the server iterates its pre-key private keys to find the matching DH and derive the initial epoch state.

External IP detection via STUN is mandatory — the STUN probe always runs at startup and the result populates ip_ext in every heartbeat. This happens once at startup and is cached for the session lifetime. If STUN fails, the agent does not fall back silently — the field is set to "unknown" and the startup error is logged, ensuring operators are never given a false sense of external IP knowledge.

6.5 Adding a Provider

Adding a new cloud provider requires implementing the three-method transport interface plus a deployment wizard. The complete implementation follows a fixed pattern — use providers/dropbox/ as the reference:

  1. Create providers/{name}/ with __init__.py, wizard.py, and transport/
  2. Implement XxxTransport(BaseTransport) — three methods: upload, download, delete; handle token refresh internally
  3. Implement XxxConfig(BaseConfig) — provider-specific credential fields (app_key, refresh_token, etc.)
  4. Implement XxxWizard(ProviderWizard) — set PROVIDER_ID, PROVIDER_NAME, TRANSPORT_DIR; implement make_config(), step_auth(), step_init_channel(); override _native_agent_extra_env() to inject STRATUM_APP_KEY etc. for the Rust build

The agent scripts for the new provider go in providers/{name}/transport/agent.sh and agent.ps1. These only need to implement _upload(), _download(), and _token_refresh() — the C2 core functions are inherited from the universal agents/templates/core.sh / core.ps1.

7OPSEC & Anti-Forensics

7.1 Artifact Tracking

Every file dropped on a target by Stratum is tracked by SHA-256 hash in the session history. This includes persistence binaries, configuration stubs, and any file written as part of a persistence technique installation. The artifact log is stored server-side in the session history CSV.

When /kill is issued, the agent receives a KILL command that triggers the full cleanup sequence: remove all installed persistence techniques, delete all tracked artifacts in reverse installation order, wipe sensitive variables from memory, and exit cleanly. The operator can also view the artifact list at any time via /artifacts.

Cloud-Side Artifact Rollback

During deployment, the wizard tracks every sensitive object uploaded to cloud storage (staged-enc: the encrypted stage-2 payload). If the wizard fails at any point after uploads have begun — network error, key generation failure, operator cancellation — Stratum automatically deletes the already-uploaded objects from the cloud provider before exiting.

This prevents orphaned encrypted payloads from remaining in the cloud folder if the deployment did not complete. Channel files (input.txt, output.txt, heartbeat.txt) are intentionally excluded from rollback: they contain no secret material and are safe to leave in place. The stub_secret is never uploaded to cloud and therefore never needs rollback.

What gets rolled back
Encrypted stage-2 payload (stage2.enc, staged-enc mode only). Not rolled back: channel files, session metadata already written to disk. stub_secret is compiled into the binary and never in cloud — no rollback needed.

7.2 Timestomping

Any file written to disk by the agent (persistence binary copy, config file, etc.) has its modification timestamp set to a value within ±30 minutes of the most recently modified system file in the target directory. This disrupts timeline-based forensic analysis, which correlates file creation/modification times to narrow the window of compromise.

Timestomping is applied automatically on every artifact write, not as an optional step. It uses native OS APIs (touch on Linux, SetFileTime on Windows) rather than shell utilities that might be logged.

7.3 Entropy Balancing

Shannon entropy is a primary signal in static analysis tools. A script file or PE section with entropy above ~6.5 b/B is classified as packed or encrypted content — an immediate red flag even without behavioral analysis. Stratum actively engineers the entropy of its artifacts at deploy time.

The wizard measures entropy after generating each script, then appends natural-language padding (facility documentation text, ~4.4 b/B entropy) in 8 KB blocks until H ≤ 5.0 b/B. The padding text is chosen to resemble legitimate system utility strings — the kind of verbose help text that any real system tool might include in its binary. Under static analysis, the file appears to be a normal utility with embedded documentation, not a packed payload.

7.4 Fileless Execution (Linux ELF Loader)

The Linux ELF loader (agents/native/linux/) uses memfd_create to achieve fully fileless script execution. The embedded agent script is written to an anonymous memory file descriptor — an in-kernel file that has no path in any filesystem:

// SYS_memfd_create = 319 on x86_64 Linux (kernel 3.17+)
fd = syscall(SYS_memfd_create, ".", 0);
write(fd, SCRIPT, sizeof(SCRIPT));
execve("/bin/bash", {"/proc/self/fd/N"}, env);
// fd stays open; child inherits it; script never touches disk

The process appears in ps as bash /proc/self/fd/5 (or similar). ls /proc/PID/fd/5 shows an anonymous file with no real path. /proc/PID/maps will show a memfd:. mapping. This execution technique is supported on Linux kernel 3.17+ (released 2014); the loader falls back to /dev/shm → /tmp with immediate unlink after spawn on older kernels.

7.5 MSVC-ABI PE vs MinGW & Rich Header Removal

The default Rust cross-compilation target for Windows from Linux is x86_64-pc-windows-gnu (MinGW). MinGW-compiled PE files carry characteristic imports: libgcc_s_seh-1.dll, libwinpthread-1.dll, and GCC-specific runtime functions. This is a known fingerprint used by EDRs and forensic tools to identify non-commercial software.

Stratum uses the MSVC target (x86_64-pc-windows-msvc) via clang-cl + lld-link + Microsoft's SDK headers (sourced through xwin). The resulting PE import table contains only standard Windows DLLs: kernel32.dll, ntdll.dll, ws2_32.dll, advapi32.dll. This profile is indistinguishable from a Visual Studio–compiled utility.

Rich Header Removal

Linkers embed a Rich header between the DOS stub and the PE signature. This 16–256 byte structure encodes which Microsoft build tools and compiler versions produced the binary — a fingerprint that allows analysts and EDRs to distinguish tool families and detect anomalies (e.g. a PE claiming to be compiled with MSVC but actually produced by a different toolchain).

The Stratum deploy wizard automatically patches the Rich header out of every EXE and DLL artifact after compilation. The patcher scans backward from the PE signature for the Rich marker, then zeroes all bytes from DanS through Rich+8 inclusive. This is done in-place with no linker flags, so the patched binary retains valid PE structure while presenting no toolchain lineage to forensic tools.

7.6 Network OPSEC

All Stratum network traffic originates from the target host to well-known cloud provider API endpoints over HTTPS. There are no custom domains, no novel TLS certificates, and no unusual destination ports. The traffic profile:

From a network detection perspective, blocking any of these destinations would disable core productivity services for the organization — a disruptive and unlikely defensive response. Traffic volume is also minimal: one HTTP request per beacon interval (typically 1–5 KB), with responses of similar size.

Jitter — log-normal distribution
The beacon interval includes a configurable jitter percentage (1–50%). Intervals are drawn from a log-normal distribution (μ and σ derived from the base sleep and jitter percentage) rather than a uniform random range. Log-normal is the natural distribution for human dwell times and system sleep durations — it produces occasional long intervals that are indistinguishable from legitimate application polling. A 60s interval with 20% jitter results in a median around 60s with occasional longer outliers, making timing analysis significantly harder than a simple min/max uniform range.

User-Agent Rotation

All agent HTTP requests use a randomly selected User-Agent string from a pool baked in at deploy time (providers/_wizard.py:_UA_POOL). The pool is updated periodically to stay within the current browser version distribution — stale UA versions (more than two major releases behind) are a reliable fingerprint for proxies that perform UA analytics (Zscaler, Palo Alto Cortex). The selected UA is fixed per-deployment, not rotated per-request, so the agent presents a consistent browser identity to the cloud provider.

UA pool requires periodic maintenance
Browser major versions advance every 4–6 weeks. Update _UA_POOL in providers/_wizard.py every 3–6 months to keep agents within the current distribution. The comment in the source marks the last update date.

MIME Boundary Randomisation (Google Drive)

The native Rust agent's Google Drive transport generates the multipart/related MIME boundary at runtime from 8 random bytes (format!("b{}", hex::encode(rand_bytes))). A static boundary string is a trivial network signature — randomising it at each upload ensures each multipart request is structurally unique.

External IP Detection (STUN)

The bash agent detects the target's external IP using a layered fallback chain. The preferred method is a direct STUN query (RFC 5389, UDP port 19302) — this works through NAT, bypasses DNS-based filtering, and requires no outbound TCP connectivity beyond the standard STUN infrastructure. Fallbacks include Google's DNS TXT record (o-o.myaddr.l.google.com @8.8.8.8) and Cloudflare's WhoAmI service.

VPN / Split-Tunnel Caveat
If the target is behind a VPN with full-tunnel routing, STUN, DNS fallbacks, and curl-based IP services will all reflect the VPN exit node's IP — not the target's true physical location. The reported external IP in the session panel is the IP as seen from the public internet at query time. This is expected behaviour and does not affect C2 functionality.

7.7 KILL — Artifact Wipe & Self-Delete

The kill command triggers a full cleanup sequence on the beacon before it terminates. The sequence is deterministic and non-interactive: the beacon completes it autonomously after receiving the task, then exits. The server waits agent_sleep + 5 seconds after uploading the KILL task before wiping the cloud folder, giving the beacon time to poll and receive it.

Cleanup sequence (all agent types)

  1. Blob wipe — the encrypted stage-2 / payload blob on disk is overwritten with cryptographically random bytes and then deleted.
  2. Persistence removal — all installed persistence techniques are torn down (cron entries, systemd units, rc.local entries, scheduled tasks, registry Run keys, WMI subscriptions, startup folder entries). The _PERSIST_DIR directory and its contents are removed recursively.
  3. Self-delete — the beacon script / binary deletes itself and any associated launcher. Mechanism varies by agent type (see table below).
  4. Channel clear — writes MZ sentinel to the input file to prevent the server from re-delivering the KILL task on the next poll cycle.
  5. Process exit — the beacon process terminates cleanly.

On Windows, a running process holds an open kernel handle on its own EXE image. DeleteFile fails with ERROR_SHARING_VIOLATION while the process is alive. The MoveFileExW(MOVEFILE_DELAY_UNTIL_REBOOT, 0x4) fallback schedules the file for deletion when the OS next boots — the binary is orphaned (persist is already gone) and will never re-execute. This is the only reliable mechanism available without a separate helper process.

VBS launcher deletion (Windows)

The deploy wizard generates a .vbs launcher next to every .ps1 artifact (stub.vbs, agent.vbs, agent_stageless.vbs). The VBS filename is always the PS1 name with the extension swapped. On KILL:

  • PS1 agents — [System.IO.Path]::ChangeExtension($env:_STUB_PATH, ".vbs") is computed and added to the same detached cmd.exe delete command, guarded by if exist.
  • Rust PE — _STUB_PATH is set by the PS1 stub before exec-ing stage-2 and is inherited by the native process. kill_cleanup() reads it via std::env::var("_STUB_PATH"), then calls Path::with_extension("vbs") to derive the launcher path and removes it.

Persist directory removal

All Linux agent techniques call rm -rf "$_PERSIST_DIR" after removing the payload file. Earlier versions used rmdir (non-recursive), which silently failed if the directory contained any extra files (e.g., from a blobsave command or operator-placed artifacts). The recursive form is used unconditionally — _PERSIST_DIR is always a wizard-generated subdirectory under $HOME/.local/share/ and is safe to remove in full.

1.5 Docker

Stratum ships a Dockerfile for containerised deployment. The image is single-stage and contains the full toolchain needed to compile agents at deploy time — Python server, Rust (rustup), clang/lld (MSVC cross-compilation), and the xwin Windows SDK. Agents are never pre-compiled: each deployment wizard run produces artifacts with unique cloud folder names, provider credentials, and encryption keys, so compilation always happens on-demand inside the running container.

Secret management
server.yml is never baked into the image — it is bind-mounted at runtime. Credentials, sessions, logs, keys, and deployment packages are all external volumes. The container image itself contains no operator secrets.
─── Image layer order (cache-optimised) ──────────────────────────────────── Base: python:3.12-slim-bookworm Layer 1 apt: curl, musl-tools, clang, llvm, lld, pkg-config, openssl, libssl-dev Layer 2 symlinks: clang-cl, lld-link, llvm-lib, llvm-rc → /usr/local/bin/ Layer 3 rustup install + targets: linux-musl, windows-msvc, unknown-none Layer 4 cargo install xwin 0.6.5 → xwin splat → /root/.xwin (~600 MB, cached) Layer 5 ENV: MSVC cross-compilation vars (linker, CC, CFLAGS, RUSTFLAGS) Layer 6 pip install -r requirements.txt Layer 7 COPY application source (stratum-server.py, server/, providers/, agents/, webui/) mkdir runtime dirs | useradd stratum | chown + chmod toolchain world-readable
Build cache
Layers 1–5 (toolchain + xwin SDK) are cached after the first build. Changing application source only invalidates Layer 7. The ~600 MB Windows SDK download happens once and is stored as a fixed Docker layer.

2.2 TLS & Browser Verification

Stratum generates a self-signed TLS certificate at install time. When accessing the WebGUI for the first time, the browser will show a certificate warning. Verify the certificate fingerprint shown by install.sh matches what your browser reports before accepting:

# Check fingerprint at any time:
openssl x509 -noout -fingerprint -sha256 -in certs/server.crt

# Output:
SHA256 Fingerprint=2A:F1:8C:...

After verifying the fingerprint, add a permanent browser exception for this certificate. Do not distribute the .crt file to add it to system trust stores in operational environments — the self-signed certificate is intentionally not trusted by default, which prevents MitM by an intermediate party that could present a CA-signed certificate.

Never disable certificate checking
Do not use --insecure / ignore TLS warnings without verifying the fingerprint first. An attacker on the network could present a forged certificate if you skip verification entirely.

2.5 Server Logging

Stratum uses Python's standard logging module configured via dictConfig in server/logging_config.py. The configuration is applied once, atomically, before uvicorn.run() is called. uvicorn receives log_config=None to prevent it from overriding the setup.

Logger namespace: all Stratum loggers live under the stratum.* hierarchy with propagate=False:

  • StreamHandler — always active, writes to stderr. Format: %(asctime)s %(levelname)-8s %(name)s: %(message)s

2.6 HTTP Security Headers & Fingerprint Reduction

The server applies a set of defensive HTTP response headers on every request, and suppresses headers that would reveal server identity or framework version. These controls are applied by an ASGI middleware layer (_SecurityHeadersMiddleware) before any route handler executes.

font-src    'self';

Fingerprint reduction: the FastAPI application is initialized with a generic title ("API"), version "1.0", and openapi_url=None — this disables the /openapi.json schema endpoint and the /docs / /redoc Swagger UIs. Combined with the empty Server header, passive reconnaissance cannot identify the framework or enumerate the API schema.

Why these headers matter for an operator tool
If an operator's browser is compromised or an operator navigates to a malicious page while Stratum is open, missing X-Frame-Options or CSP makes clickjacking attacks viable against the WebGUI. These headers are standard hardening for any web admin panel, even one accessible only on a private network.

3.2 Local Mode

The default mode. Operator accounts are defined directly in server.yml under the users key. Passwords are stored in cleartext — the file is the trust boundary and must be chmod 600.

auth_mode: local

users:
  - username: alice
    password: "changeme"
  - username: bob
    password: "changeme2"

All operators have equal privileges. There is no role or permission system. To add or revoke an account, edit server.yml and restart the server. At boot, prefs files for users no longer present in the list are automatically deleted.

Login attempts are rate-limited per client IP: 5 failures in 300 seconds triggers a 60-second lockout. Failed-attempt counters and lockout entries are held in memory and purged automatically when they expire — the memory footprint remains bounded regardless of scan or probe volume. Lockout state does not survive a server restart.

Protect server.yml
server.yml contains operator passwords and the JWT signing secret in cleartext. Run chmod 600 server.yml immediately after creation.

3.3 OIDC-Manual Mode

Delegates authentication to an external OIDC provider (Keycloak, Azure AD, Okta, or any standard OIDC-compliant IdP). Access is restricted to a pre-declared whitelist of identities defined in server.yml. The lifecycle is identical to local mode: at boot, prefs files are created for whitelisted identities and purged for identities that have been removed.

auth_mode: oidc-manual

oidc:
  provider_url: https://keycloak.example.com/realms/stratum
  client_id: stratum-c2
  client_secret: "your-client-secret"
  identity_claim: email          # claim used as stable identity key
  display_claim: preferred_username  # claim shown in WebUI
  allowed_identities:
    - alice@corp.com
    - bob@corp.com

To revoke access: remove the identity from allowed_identities and restart. The prefs file is deleted automatically at the next boot.

Two independent OIDC claims control how an operator appears in the system:

ParameterPurposeNormalised?Default
identity_claimStable key used for whitelist/blocklist checks, prefs file name, and JWT subYes — lowercased and strippedemail

3.6 Login Page Behaviour

The login page adapts automatically based on the server's auth_mode. Operators navigate to https://<server>:<port>/ — the server redirects unauthenticated requests to the login page.

  • local — operator sees a username + password form. Enter credentials and submit. A JWT is issued on success and stored as a session cookie; the browser redirects to the WebGUI.
  • oidc-manual / oidc-auto — the credential form is hidden and replaced by a single Sign in with OIDC Provider button. Clicking it redirects the browser to the provider's authorization page (Keycloak, Azure AD, Okta, etc.). After successful authentication, the provider redirects back to Stratum with an authorization code; the server verifies the token, checks the identity against the whitelist (oidc-manual) or blocklist (oidc-auto), issues a JWT, and redirects to the WebGUI. No credentials are entered in Stratum directly.

OIDC errors (access denied, invalid state, missing claim, provider unreachable) are surfaced as inline messages on the login page — never as raw browser errors. An invalid JWT or expired session redirects back to the login page automatically.

3.7 Startup Validation

The server validates server.yml at boot and exits with a clear diagnostic message if any of the following conditions are detected:

  • auth_mode is not one of local, oidc-manual, oidc-auto
  • auth_mode: local with no entries in users[]
  • auth_mode: local with a user entry missing username or password
  • auth_mode: oidc-manual or oidc-auto with missing provider_url, client_id, or client_secret
  • auth_mode: oidc-manual with an empty allowed_identities list
  • server.yml is not valid YAML

The server never starts in a partially configured state — fail-fast is intentional.

Before ending an engagement, work through this checklist using the Artifacts tab:

  1. Open the Artifacts tab and review On-Target Artifacts. For each item still marked on target, issue a shell rm/del or use a /persist remove <id> command to clean it up, then mark it as removed.
  2. Review Uploaded Files. Use the Delete button for each file to send the removal command and mark it removed.
  3. Send /kill to terminate the agent — this removes all persistence techniques, deletes the staged blob from the target disk, then terminates the process.
  4. Delete the session via the Control tab or session header — see §5.9.

/kill runs a full cleanup sweep before exiting: removes all installed persistence, wipes the on-disk blob. /stop is a graceful shutdown with no cleanup. Use /kill at end of engagement, /stop only when you intend to resume later and the target state is already clean.

Background cloud cleanup

Cloud folder deletion runs in a background thread so the operator is not blocked waiting for the agent to poll. The sequence is:

  1. KILL sent — the KILL task is written to the dead-drop input path.
  2. Local cleanup (immediate) — session removed from the manager, deployment directory, upload records, history log, and downloads deleted. The progress modal closes at this point.
  3. Wait — the background thread sleeps agent_sleep + 5 seconds. This guarantees the agent has time to poll and receive the KILL before the cloud folder is deleted. Agents with long sleep intervals (e.g. 1h30m) hold the thread for the full cycle — the operator remains unblocked during this time.
  4. Cloud delete — output file, heartbeat file, and the entire session folder are deleted from the provider.
  5. Notification — a session.wipe_done WebSocket message is broadcast to all operators. The session row is removed from the list and a toast confirms success or reports the error.

Wiping badge

While the background thread is running, the session row stays visible in the Session List with a pulsing ⟳ WIPING badge instead of the normal status pill. This signals to all operators that the session has been terminated locally but cloud cleanup is still in progress. The row disappears automatically when the cloud delete completes.

Full cloud folder deletion
The Cloud channel files option deletes not just the three dead-drop files but the entire cloud folder for this session. Deletion is recursive and provider-aware: Dropbox, OneDrive, and SharePoint use a single recursive API call; Google Drive resolves the folder's file ID then issues a DELETE /files/{id}; S3 lists all objects under the folder prefix and deletes each one (S3 has no real folders).
Preserve history for post-op review

Total deploy deletion

Deleting a session removes it from the live session list but does not remove the deployment package (keys, binaries, guide) from the deployments/ directory on the server. To fully remove a deployment:

  1. Delete the session with Cloud channel files enabled (recursively deletes the cloud folder and all its contents)
  2. Open 📦 Tradecraft and delete the corresponding deployment package

Deleting the Tradecraft package removes the RSA private key for that session from the server. Once deleted, encrypted past responses cannot be decrypted — this is a one-way operation. Do this only after all relevant data has been extracted and saved locally.

Key deletion is permanent
Deleting a Tradecraft package irrecoverably destroys the session's RSA private key. Past encrypted responses stored in the cloud (if any remain) can never be decrypted again. Download and archive everything you need before deleting the package.

/stop    — graceful shutdown: agent finishes any pending command, then exits cleanly

Both commands are asynchronous — the agent picks them up on its next checkin cycle. After sending /kill or /stop, the session will go IDLE then DEAD as the heartbeat stops. Delete the session after the status reaches DEAD to confirm the agent is no longer running.

6Command Reference

6.1 Shell Pass-Through

Any input in the session REPL that does not begin with / is treated as a shell command. The controller wraps it with the current working directory context and sends it to the agent, which evaluates it as native shell code — eval in Bash on Linux, Invoke-Expression in PowerShell on Windows. stdout and stderr are captured and returned together.

Supported shell syntax: all native shell constructs work as expected.

# Pipes and filters
ps aux | grep python | awk '{print $2}'
cat /etc/passwd | cut -d: -f1 | sort

# Redirections
ls -la /tmp > /tmp/listing.txt
curl -s http://internal-api/data 2>/dev/null

# Command chaining
id && whoami && hostname
mkdir /tmp/.work && cd /tmp/.work

# Variable expansion and substitution
echo "running as $(whoami) on $(hostname)"

# Windows equivalents
dir C:\Users | findstr /i "admin"
Get-Process | Where-Object { $_.CPU -gt 10 } | Select-Object Name,CPU

Working directory persistence: the session tracks the current working directory across commands. A cd command updates the CWD for all subsequent commands in that session, exactly like a persistent shell.

cd /var/www/html
ls -la              # runs in /var/www/html
cat config.php      # still in /var/www/html

# Windows
cd C:\Users\jdoe\AppData\Local
dir                 # runs in the new path

Quoting: quote paths with spaces normally — the shell interprets quoting exactly as it would locally.

ls "/home/user/My Documents"
Get-Content 'C:\Program Files\App\config.ini'
Shell pass-through is not interactive
The shell is not a PTY — there is no interactive session. Each command is a one-shot execution. Commands that require interactive input (like sudo prompting for a password, vi, ssh) will hang until the command timeout expires. Use explicit non-interactive flags (sudo -n, echo "pass" | sudo -S) or the built-in slash commands instead.

The /creds family collects credential material from the target for offline cracking or lateral movement. It is designed for the Stratum use-case: grab what you need to re-establish access, then exfiltrate through the cloud channel.

Agent support: Rust native + PowerShell only
The /creds module requires binary protocol capabilities (SMB2/NTLMSSP, ASN.1/DER, AES-GCM) that the bash agent cannot provide. Deploy the Rust native agent for full cross-platform credential harvesting (Linux + Windows), or the PowerShell agent for Windows-only coverage. The bash agent will return ERROR: unknown task type for any /creds command. See §3.5 for the complete feature parity matrix and implementation-level differences between Rust and PS1.

Cloud credentials (AWS, Azure, GCloud, Docker, Kube) are parsed and displayed inline. SSH keys are classified as encrypted/plaintext.   • /creds sam reads registry keys via API with REG_OPTION_BACKUP_RESTORE — no reg.exe process, no hive files on disk, no command-line telemetry. Generates minimal registry access events (ID 4656/4663) which are typically not forwarded unless audit-object-access is explicitly enabled.

  • /creds harvest files are exfiltrated via the normal Stratum cloud channel — large dumps (browser DBs) may take multiple poll cycles.

6.7 In-Memory & Fileless Execution

These commands load and run binaries or scripts without writing anything to disk on the target. Binaries are executed in the agent's process memory; scripts are piped to the interpreter's stdin. All commands are Rust native agent only. Platform support varies per command — see the callout below.

Agent support: Rust native only
In-memory and fileless execution requires low-level memory management (VirtualAlloc, COM vtable calls, section mapping, relocation patching, stdin pipe control) that is fundamentally impossible in script interpreters. Deploy the Rust native agent for BOF, .NET assembly, PE/ELF in-memory execution, and fileless script execution. Platform support: /bof, /assembly, /assembly-amsibypass are Windows only. /memexec, /script are cross-platform (Win+Linux). /script-amsibypass is Windows PowerShell only.
/bof <file.o> [args]Execute a Beacon Object File (COFF) in-memory. The agent parses COFF headers, resolves relocations and imports, maps sections with correct permissions, and calls the entry point. Output is captured via internal output buffer. Windows only.
/assembly <file.exe> [args]Execute a .NET assembly in-memory via CLR hosting. The agent initializes the .NET CLR (v4.0.30319), creates an AppDomain, loads the assembly bytes via _AppDomain::Load_3, and invokes the entry point via _MethodInfo::Invoke_3. Console output is captured via pipe redirection with a dedicated reader thread (prevents deadlocks on large output). An embedded ConsoleReset helper rebinds Console.Out after pipe redirect. Supports passing command-line arguments as string[] args. Windows only.
/assembly-amsibypass <file.exe> [args]Same as /assembly but with a patchless AMSI bypass applied before loading the assembly. The agent sets a CPU hardware breakpoint (DR0) on AmsiScanBuffer and installs a Vectored Exception Handler. When AMSI calls AmsiScanBuffer, the CPU raises a debug exception; the VEH intercepts, sets the return value to AMSI_RESULT_CLEAN, and skips the function body. Zero VirtualProtect, zero memory writes on amsi.dll — evades Behavior:Win32/AMSI_Patch_T behavioral detections. The breakpoint is removed after execution. Use this when Defender blocks assemblies like Rubeus, Seatbelt, or SharpUp. OPSEC note: patchless — no memory modifications to amsi.dll. Breakpoint is per-execution, not persistent.
/memexec <file> [args]Execute a native binary entirely in-memory — nothing written to disk. Windows: reflective PE loading — maps sections, applies relocations, resolves imports, calls entry point. Linux: memfd_create + execve — creates an anonymous file descriptor in memory, writes ELF bytes, executes via /proc/self/fd/N. Cross-platform (Win+Linux), Rust native agent only.
/script <file> [interpreter]Execute a script entirely fileless. The script is staged in the cloud provider, downloaded to agent memory, and piped to the interpreter's stdin — nothing is written to disk. Interpreter auto-detection: .ps1 or hint ps1 → PowerShell; .bat/.cmd or hint cmd → CMD; shebang #!/bin/bash → bash; shebang #!/usr/bin/python or hint python → python3; default → PowerShell on Windows, /bin/sh on Linux. The optional second argument overrides auto-detection: ps1, cmd, bash, python, sh. Windows processes run with CREATE_NO_WINDOW. Cross-platform.
/script-amsibypass <file> [interpreter]Same as /script but with patchless AMSI bypass: sets a CPU hardware breakpoint (DR0) on AmsiScanBuffer + Vectored Exception Handler before spawning PowerShell. The VEH intercepts AMSI scan calls and returns AMSI_RESULT_CLEAN without modifying any memory in amsi.dll. Evades Behavior:Win32/AMSI_Patch_T detections. Breakpoint removed after execution. Windows PowerShell only — on Linux the AMSI flag is ignored and the script runs normally.

7.1 Cold Restart and the HW-Keyed Blob (ddb)

In staged-enc and stageless-enc modes, the agent writes a hardware-keyed blob (ddb cache) to disk after its first successful run. This blob stores the decrypted C2 configuration encrypted under a key derived entirely from local machine hardware:

# hw_key derivation (all platforms):
hw_key = SHA-256(MachineGuid + MAC_address + SALT)   # 32-byte deterministic key

# Blob format (Linux / bash stub):
AES-256-CBC(config_string, hw_key)   → .stratum_ddb   # OpenSSL PBKDF2, 210 000 iter

# Blob format (Windows / DPAPI):
DPAPI(config_bytes)                  → stratum_ddb.dat  # user-bound, machine-bound

On every subsequent restart, the stub checks for the ddb blob before attempting any cloud fetch. If the blob decrypts cleanly, the agent boots instantly with no network traffic — the cloud folder is not accessed at all. This means:

  • Cold restarts after reboot are fast and silent — no cloud round-trip
  • The agent survives even if stage2.enc has already been deleted from cloud (as it will be after first heartbeat in staged-enc mode)
  • The blob is machine-bound — copying it to a different host decrypts to garbage
─── Cold Restart · Decision Flow ────────────────────────────────────────── Stub executed (after reboot / process restart) │ ├─ Check ddb blob on disk │ found + hw_key decrypts → fast boot (no network) │ agent starts from cached config │ └─ ddb missing or corrupted │ ├─ [staged-enc] → download stage2.enc from cloud │ (will fail if stage2.enc deleted — expected) │ → on failure: agent exits cleanly, no crash │ └─ [stageless-enc] → decrypt baked config blob with stub_secret always succeeds — stub_secret is in the binary
ddb blob and /blobsave
If the ddb blob is deleted (e.g. by IR cleanup, manual deletion, or OS re-image with the stub still present), issue /blobsave from the session REPL while the agent is active. This forces the agent to re-write the blob immediately, restoring cold-restart capability without any cloud interaction.

7.2 Sleep & Jitter Tuning

The sleep interval and jitter percentage determine the agent's network fingerprint. The native Rust agent draws beacon intervals from a log-normal distribution parameterized by the configured sleep and jitter values. Unlike uniform jitter (which creates a rectangular timing distribution easily identified in PCAP), log-normal produces a long-tailed distribution that mimics legitimate application polling patterns. Finding the right balance between responsiveness and stealth depends on the target environment:

ScenarioRecommended SleepJitterRationale
Active engagement (operator present)30–60s15–20%Reasonable responsiveness, low timing regularity
Long-haul persistence (unattended)120–300s20–35%Minimal network footprint, high timing irregularity
Ultra-low-profile (hostile IR ongoing)600–1800s30–50%Commands take 10–30 min to arrive; virtually no network signature
Testing / lab10–15s5%Fast iteration; not suitable for production

Change sleep and jitter live without redeploying:

/sleep 300    # change to 5-minute interval
/jitter 30    # ±30% = actual interval 210–390s

7.3 Maintenance Windows

A maintenance window defines a time range during which the agent will not beacon. This is useful for suppressing activity during business hours when network monitoring is more likely. Outside the window, the agent operates normally.

Maintenance windows are configured at deploy time in the wizard (Step 3). They cannot be changed post-deployment without redeployment. The time range is evaluated against the target system's local time, not the server's timezone.

# Example: agent only active between midnight and 6am
Window: 00:00 → 06:00

# Outside the window: agent beacons normally
# Inside the window:  agent skips all beacon cycles, stays silent
Window Design
Set the window to cover working hours, not off-hours. The agent should be active when operators are present and targets are quiet (nights, weekends). Example: 08:00 → 18:00 suppresses activity during the target's business day.

7.4 Kill Date

A kill date is a YYYY-MM-DD date baked into the agent at compile/deploy time. On or after that date, every agent — Rust native, bash, and PowerShell — performs a full self-destruct sequence at the start of its next beacon cycle:

  1. Removes all installed persistence techniques (scheduled tasks, registry keys, cron entries, systemd units, startup folder entries)
  2. Wipes and deletes the local hw-keyed blob (ddb file on disk)
  3. Deletes its own binary from disk
  4. Exits the process

The kill date is optional — leaving the field empty disables the feature entirely. It is configured in the Deploy Wizard under Kill Date (in the Guardrails section, alongside Window Start/End). It cannot be changed post-deployment without redeployment.

# Wizard field (Step 3 — Guardrails):
Kill date: 2026-12-31

# Agent check logic (each cycle, before heartbeat):
if today >= kill_date:
    persist_remove_all()
    delete blob
    delete self
    exit
Engagement Hygiene
Always set a kill date that covers the engagement window plus a safety margin (e.g. SoW end + 7 days). This ensures no agent survives past the authorised period, even if the operator forgets to issue a /kill command.
Platform Notes
On Linux/macOS, the running binary is unlinked immediately (unlink while open is safe on Unix — the inode persists until the process exits but the directory entry is removed). On Windows, DeleteFile on the running executable typically fails; the binary is left on disk as an orphaned file with no persistence mechanism pointing to it — effectively inert.

7.5 Blob Management

In persistence techniques that install a binary (scheduled task, service, registry), the agent copies itself to a target disk path — the blob path. This path is configured at deploy time (Blob Path field in the wizard, Step 3). The blob is tracked in the session artifact log.

The blob path should mimic a legitimate system binary location:

# Good blob paths (blend with legitimate software)
C:\Users\%USERNAME%\AppData\Local\Microsoft\SystemUpdateHelper\
C:\Windows\System32\DriverStore\FileRepository\  (requires admin)
/usr/lib/systemservices/updatehelper             (requires root)
~/.local/lib/python3.10/site-packages/utils/     (user-priv)

# Avoid obvious paths
/tmp/agent    — cleaned on reboot, obvious location
C:\Temp\      — suspicious, frequently audited

The /kill command removes the blob along with all other tracked artifacts. The blob is also automatically removed when a persistence technique is individually removed via /persist remove <id>.

7.7 Auto-Update System

Stratum checks GitHub for new releases once at server startup. If a newer version is available, operators see an amber banner in the topbar after login. Clicking the banner opens a modal with release notes and an "Update Now" button.

Configuration

# server.yml
auto_update:
  enabled: true
  repo: "OWNER/stratum-c2"  # GitHub owner/repo

Set enabled: false or leave repo empty to disable the check entirely.

Update Process

  1. Preflight — verifies git is installed, the project is a git repository, and checks working tree status
  2. Fetch & merge — runs git fetch origin main + git merge origin/main --no-edit
  3. Dependencies — if requirements.txt changed, runs pip install -r requirements.txt
  4. Notification — broadcasts result to all connected operators via WebSocket

Data Safety

All operational data is in .gitignore and never touched by git merge:

  • sessions/ — session profiles and state
  • keys/ — RSA keypairs
  • logs/ — command history and chat logs
  • credentials/ — provider credential profiles
  • server.yml — server configuration
  • certs/ — TLS certificates

On merge conflict, the update aborts cleanly via git merge --abort — no damage. Restart is always the operator's choice.

REST Endpoints

GET  /api/v1/update/status     # current update state
GET  /api/v1/update/preflight  # pre-flight checks
POST /api/v1/update/apply      # apply update
POST /api/v1/update/check      # force re-check
